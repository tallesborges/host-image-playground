Can the page read the contact?

This page is the product. It shows the same synthetic contact, Alice Example, in two ways. A different origin, the host, owns the contact data. The page gets only an opaque alias. With the IMG idea, the page shows two images from the host: the avatar as a PNG picture and the name as SVG text. With the iframe idea, the page embeds one frame from the host. Each test runs JavaScript on this page and tries to get the avatar or the name.

Synthetic data and public URLs. This demo tests only one thing: what JavaScript on this page can read in a browser. It is not access control. Anyone can open the host URLs directly, for example with a browser or curl. In a real app, the host gives each product its own aliases. The host resolves an alias only together with the product that it knows is running, not with a product id in the URL.

1. Same contact, two ways

Both show the avatar and the name to the user. The question is: can this page's JavaScript get them? The control is the same two images from this page's own origin. They must be readable. This shows that the tests can find a leak.

2. Video and audio

The same test for <video> and <audio>, with synthetic files that have a known signal: a video with a red and a blue half, and a 440 Hz tone. The tests try to get the file, a frame's pixels, or the audio samples. "Only zeros" counts as blocked only if the same-origin control gives the real content in the same browser. The page can always see the duration, the video size, the play time, and the events. Click a Run button or "Run all tests": audio plays only after a click, and you hear nothing.

3. Search and select (iframe idea only)

The frame runs the search. When you select a contact, the frame sends only the contact alias to this page. This page can send two commands to the frame. The log checks each message for a name. An image cannot do this: it cannot run search or send events.
